# ZK Whitelist Claim

An anonymous whitelist claim system built with [Noir](https://noir-lang.org/) and [Barretenberg](https://github.com/AztecProtocol/barretenberg) (UltraHonk), deployed as a Solidity smart contract verifiable on any EVM chain.

A member of a private whitelist can prove eligibility and claim a reward without revealing which member they are, using a zero-knowledge Merkle membership proof. The design also prevents proof theft (front-running) and double-claiming, using techniques from Tornado Cash and Semaphore.

## How it works

1. Each whitelisted member is privately given a `(nullifier, secret)` pair.
2. The tree published on-chain contains only `leaf = hash(nullifier, secret)` for each member — never their identity.
3. To claim, a member proves in zero-knowledge that they know a `(nullifier, secret)` pair whose hash is a leaf in the tree, without revealing which leaf.
4. A public `nullifier_hash = hash(nullifier, recipient)` is revealed. It serves two purposes:
   - **Prevents double-claiming**: the contract tracks used nullifiers.
   - **Prevents front-running**: the hash is cryptographically bound to the claiming address, so a stolen proof cannot be resubmitted by anyone but its intended recipient.

```
Noir circuit  ->  Barretenberg proof  ->  Solidity verifier  ->  WhitelistClaim.sol
(Merkle proof     (UltraHonk,             (auto-generated)      (nullifier tracking,
 + nullifier)      keccak oracle)                                recipient binding)
```

## Setup

Requires [Nargo](https://noir-lang.org/) (Noir toolchain), [Barretenberg](https://github.com/AztecProtocol/barretenberg) (`bb`), [Foundry](https://book.getfoundry.sh/), and Node.js.

```bash
noirup --version 1.0.0-beta.11
bbup -v 0.87.0
foundryup
```

```bash
cd circuits/whitelist && nargo compile
cd ../../scripts && npm install
```

## Usage

### 1. Generate a proof

Builds a 16-member Merkle tree, proves membership for member 0:

```bash
cd scripts
node generate-proof.js
```

This writes `proof-data.json`, consumed by the Foundry test.

### 2. Regenerate the verification key and Solidity verifier

Required any time the circuit changes:

```bash
cd circuits/whitelist
bb write_vk --scheme ultra_honk --oracle_hash keccak -b target/whitelist.json -o target
bb write_solidity_verifier --scheme ultra_honk -k target/vk -o target/Verifier.sol
cp target/Verifier.sol ../../contracts/src/Verifier.sol
```

### 3. Run tests

```bash
cd contracts
forge test -vv
```

Three tests cover the three security guarantees:

| Test | What it verifies |
|---|---|
| `test_ValidClaimSucceeds` | A legitimate proof is accepted |
| `test_RevertWhen_NullifierAlreadyClaimed` | Double-claiming is rejected |
| `test_RevertWhen_WrongRecipient` | A stolen proof submitted by the wrong address is rejected |


## Security considerations

- Nullifiers are tracked in a `mapping(bytes32 => bool)`, checked before the (expensive) ZK verification to fail cheaply on replay attempts.
- `nullifier_hash = hash(nullifier, recipient)` binds every proof to one specific claiming address, making a copied proof from the public mempool useless to anyone but its intended recipient.
- The verifier contract (`Verifier.sol`) is generated code and should never be hand-edited; only regenerated from a trusted `bb write_solidity_verifier` run.

## What this project demonstrates

- **Zero-knowledge circuit design (Noir)**: Merkle membership proofs, nullifier schemes for anonymity + replay protection
- **The UltraHonk proof format** and its EVM verification constraints (precompiles, public input layout)
- **End-to-end ZK tooling**: Nargo → Barretenberg → Solidity, including the practical version-compatibility issues of this still-young ecosystem
- **Foundry testing patterns** for ZK-verified contracts (`vm.prank`, `vm.expectRevert`)
